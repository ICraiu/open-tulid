Refactor Tulid to remove per-task execution contracts entirely while preserving the project-level global contract and global end-to-end acceptance rules.

Work only in `/home/rawsteel/repo/open-tulid`. Do not modify the Wealthy Scholar application source. Do not start or stop Tulid. Do not start any Tulid runtime, worker, proxy, Docker worker, or model request. Do not commit or push. Inspect and modify code/configuration/tests only.

Product decision:
- Delete the idea of a per-task contract generated for every implementation task.
- Do not generate a contract to make a task pass tests.
- Do not make implementation tasks wait for `PrepareExecutionContract`.
- Do not re-run an LLM to author a contract before each task.
- A task should directly describe the work to the implementation worker.
- Later, a separate task may test a feature and repair it; that is normal implementation/review work, not contract generation.

What remains:
- Keep one project-level global contract in the project configuration (for example the project contract.yaml/config referenced by Tulid).
- The global project contract defines reusable environment and acceptance policy for every task:
  - worker/container ownership and clean workspace behavior;
  - runtime configuration location outside the project change surface;
  - global allowed/forbidden safety rules;
  - global end-to-end acceptance profile and deterministic baseline commands;
  - global retry/recovery policy;
  - registered invariant/validation policy;
  - observability and artifact/provenance requirements.
- Global acceptance is applied by Tulid to the completed project/task outcome. It is not written anew by an LLM for each task.
- Task-specific tests remain ordinary implementation requirements when a task naturally needs them, but Tulid must not invent a per-task contract around them.

Current problem to remove:

- LLM contract generation produced blank argv, prose invariant IDs, invalid/duplicate contracts, and prompt compile failures.
- The task was repeatedly reset to Todo and consumed model time without implementation progress.
- A valid implementation was rejected because worker runtime configuration leaked `opencode.json` into the project and npm workspace ownership was wrong. These are global runtime concerns and belong in the project contract/executor, not a task contract.
- Scheduler cooldown/retry behavior around contract failures made the system appear idle.
