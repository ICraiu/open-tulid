## Final product decision

A global project contract has exactly one purpose:

> Define commands that Tulid must execute successfully to verify the project.

The global contract is configured once in the project configuration. It is not generated by an LLM per task or per run.

Example:

```yaml
contract:
  commands:
    - name: backend_tests
      argv: [npm, test, --prefix, backend]
      working_directory: .
      timeout_seconds: 300
    - name: project_build
      argv: [npm, run, build]
      working_directory: .
      timeout_seconds: 300
```

Use the actual existing project configuration/schema conventions; the example is conceptual.

## Remove these ideas

Remove or deprecate all contract behavior based on:

- predicted or allowlisted files;
- `change_surface.add/edit/forbidden` as contract acceptance;
- requiring the worker to declare anticipated files;
- invariant IDs or prose invariants;
- per-task generated ImplementationContract artifacts;
- `PrepareExecutionContract` in the implementation path;
- task-specific contract generation to decide acceptance;
- treating a task as invalid merely because it creates a new directory or file;
- contract checks duplicated into task artifacts.

A worker is allowed to create, edit, rename, and delete files required by its task. Tulid must not reject a completion because a file was not predicted in advance. Do not make file diffs part of the contract acceptance decision.

## What remains

- Project configuration contains the global command list.
- Commands are explicit, deterministic, non-empty argv arrays.
- Tulid runs those commands in the completed worker workspace.
- A command passes only when its configured exit expectation is met.
- Command stdout/stderr and exit codes are retained as verification evidence.
- Timeouts, command-not-found, nonzero exits, and malformed command definitions produce clear feedback.
- Ordinary task text still tells the worker what to implement.
- Task-specific tests may be mentioned in ordinary task text, but are not turned into generated contracts.
- Todo ImplementationTask schedules directly to ImplementTask.
- Rejected completion feedback and bounded retries remain, but retries reuse the same task and global command policy.
- SelfReview remains an ordinary workflow transition and can run the global commands again if configured.
- Runtime/container ownership and generated runtime configuration may remain infrastructure concerns, but must not be confused with contract acceptance or file allowlists.

## Important distinction

Do not replace file allowlists with a broader file allowlist. Delete file-based contract acceptance entirely. The global contract is commands only.

Do not invent a new LLM authoring step. Project configuration is authoritative and human/edit-time authored.
