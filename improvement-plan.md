  # Make Qwen Produce Runnable, Usable Changes

  ## Summary

  Reorient Tulid around a closed local-model loop: precise executable task contract → Qwen implementation →
  deterministic acceptance → targeted Qwen repair → integration only after acceptance. Do not add a high-level-
  model code-review stage.

  The current system has strong planning prompts and Panalyzer-aware authoring, but the guarantees stop too
  early: Panalyzer is mostly injected text, task contracts can still be too large, validation is transition-
  global rather than task-specific, and passing npm test/npm run build does not prove a user-visible flow works.

  Codex plan + Panalyzer graph
          ↓
  validated task contract + acceptance manifest
          ↓
  Qwen: inspect → implement → focused test → submit
          ↓
  trusted unit/build/vertical-slice checks
          ↓
  pass → promote; fail → compact diagnostic packet → Qwen repair

  ## 1. Make Panalyzer a Runtime Contract, Not Prompt Background

  - Add a Tulid integration layer for Panalyzer rather than invoking it only through STT-clipboard agent prose.
  - For repository-backed planning:
      - run and preserve a full Panalyzer scan against the exact base commit;
      - validate the generated panalyzer-proposal.json;
      - reject planning completion on Panalyzer errors and require explicit acknowledgement/resolution of
        warnings;

      - store the scan SHA, proposal SHA, and proposal identities with the implementation specification.

  - Replace text-only proposal coverage with structured task metadata:
      - proposal_files, proposal_methods, proposal_references;
      - allowed_paths, allowed_symbols, forbidden_paths;
      - base_commit.

  - Validate derived tasks against the proposal:
      - every declared proposal entity is assigned to exactly one task unless marked deferred;
      - every task entity exists in the proposal;
      - dependencies follow reference edges rather than the planner’s prose alone;
      - task change surfaces do not overlap unless explicitly serialized.

  - Re-scan after an accepted task and compare the structural delta with the task’s assigned proposal subset.
    Reject unexpected new/changed files, symbols, and reference edges; permit declared implementation details
    that Panalyzer cannot parse through an explicit per-task exception field.

  ## 2. Replace “Long Markdown Task” with an Executable Qwen Work Order

  Keep the human-readable Markdown task, but add a compact machine-readable task-contract.json generated by Tulid
  and mounted in .open-tulid/.

  Required fields:

  - objective: one observable behavior;
  - base_commit;
  - allowed_paths, forbidden_paths, allowed_symbols;
  - required_interfaces: exact signatures or typed pseudocode;
  - preconditions and prerequisite task IDs;
  - acceptance_checks: named commands plus expected observable results;
  - changed_code_budget and max_files;
  - proposal_coverage;
  - repair_limit.

  Change task authoring rules:

  - Size implementation tasks by uncertainty and integration seam, not a fixed “3–4 tasks per module” rule.
  - Default to one behavior, one integration seam, and roughly 1–3 production files; split whenever Qwen must
    choose architecture, discover an interface, or coordinate multiple independent callers.

  - Make 500 changed lines an absolute exceptional ceiling, not the normal target. Start with a 150-line
    production-code budget and tune it from run data.

  - Require each task to name one narrow test first, then one vertical-slice acceptance check. “npm test” alone
    is never sufficient.

  - Remove mandatory Mermaid diagrams from Qwen-facing implementation tasks. Preserve diagrams in planning
    artifacts; use their tokens for exact contracts, commands, and expected outputs.

  - Give Qwen a short, fixed execution protocol: read contract → inspect only named seams → make smallest change
    → run targeted check → run acceptance check → submit actual diff/evidence. Put verbose parent/spec context
    behind the compact contract, and inject only Panalyzer entities relevant to that task.

  ## 3. Add General-Purpose Runnable Acceptance Profiles

  Introduce a project-owned, versioned acceptance.yaml (or equivalent workflow declaration) that declares
  reusable capabilities rather than STT-specific tests:

  - unit: focused test command;
  - build: package/build command;
  - static: formatter/type/lint command;
  - component: in-process or containerized dependency test;
  - vertical_slice: start application with declared fakes/fixtures, exercise a public interface, assert an
    observable result;

  - host_smoke: optional capability-gated test for real hardware, OS integration, or external services.

  Each implementation task selects one or more named profiles in its task-contract.json; Tulid resolves and runs
  them in a clean verification workspace. Profiles define command, timeout, environment allowlist, fixture setup/
  teardown, readiness condition, action, and assertions.

  For a desktop/audio app such as STT-clipboard, the vertical slice would use fake recorder, STT, LLM, clipboard,
  and hotkey boundaries to prove one complete input-to-output flow. A real microphone/global-hotkey check is a
  separate optional host-smoke profile. The same model works for CLIs, APIs, workers, web apps, libraries, and
  services.

  Require every product-facing task to have at least one deterministic vertical-slice profile or an explicitly
  justified exemption. Keep hardware/network tests non-blocking unless the configured runner advertises the
  required capability.

  ## 4. Turn Rejection into a Bounded Qwen Repair Loop

  - On failed trusted validation, keep the same workspace and give Qwen a compact repair packet containing:
      - failing command and normalized stderr;
      - affected acceptance-check name;
      - current diff summary;
      - contract boundary reminder;
      - remaining repair attempts.

  - Qwen may repair only within the original allowed surface. It must rerun the failed narrow check before
    rerunning the full selected profile set.

  - Classify failures deterministically:
      - implementation_failure: retry Qwen up to two repairs;
      - contract_failure: return task to planning/breakdown with structured feedback;
      - environment_failure: mark blocked without changing code;
      - baseline_failure: record and do not spend Qwen attempts.

  - Add a separate no-edit VerifyTask/AcceptanceReview transition. The current SelfReview requires changed files,
    which conflicts with its own instruction to submit no patch when no defect exists and encourages gratuitous
    edits. Verification must accept an empty diff and require fresh test evidence instead.

  - Do not use Qwen self-review as the principal quality gate. Use it only for a cheap targeted consistency pass
    after implementation; trusted acceptance profiles determine promotion.

  ## 5. Enforce the Boundary and Integrate Only Proven Work

  - Build each verification workspace from the exact task base commit and retain a baseline manifest. Determine
    changed files from a trusted diff, not only Qwen’s submitted list.

  - Enforce allowed_paths, output-artifact rules, deletion/rename policy, change-size budget, and declared
    generated-file rules before validation.

  - Promote only the trusted diff after all required acceptance profiles pass; record base commit, diff hash,
    profile results, Panalyzer before/after summaries, and repair history.

  - Serialize overlapping tasks and tasks that edit a shared integration seam. Run independent tasks in parallel
    only when their structured allowed paths and proposal edges do not conflict.

  - If the canonical repository has advanced since the task base commit, rebase/replay the patch into a fresh
    verification workspace and rerun the selected checks before promotion.

  ## Test Plan and Success Metrics

  - Add fixture projects for CLI, HTTP service, library, and desktop-style fake-adapter vertical slices.
  - Cover: proposal/task coverage mismatch, overlapping task surfaces, unexpected structural delta, forbidden
    edit, no-op verification, failed acceptance repaired by Qwen, baseline/environment classification, stale-base
    replay, and promotion refusal.

  - Run a fixed evaluation corpus of representative tasks before and after rollout. Record:
      - first-pass acceptance rate;
      - acceptance rate after bounded repair;
      - vertical-slice pass rate;
      - unexpected-file/symbol rate;
      - rework or rollback rate;
      - token/time per accepted usable change.

  - Roll out in order: structured contracts and evidence capture → acceptance profiles → repair loop and no-edit
    verification → Panalyzer delta enforcement → parallelism based on declared conflict data.

  ## Assumptions

  - The high-level LLM remains responsible for direction, specification, and task generation, but never routinely
    reviews Qwen diffs.

  - Usability means deterministic proof of a meaningful public behavior where possible; real hardware/service
    verification is capability-gated rather than universally required.

  - Existing project-specific npm test and npm run build commands migrate into named acceptance profiles rather
    than remaining hard-coded transition requirements
