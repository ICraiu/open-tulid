## Product decision

Remove the entire idea of parsing OpenCode errors or detecting a specific doom loop.

Tulid does not need to know whether OpenCode stopped because of `doom_loop`, another permission denial, a crash, or another agent failure. For worker supervision, all unexpected worker exits are equivalent.

The observability signal is simply:

```text
Is the OpenCode worker process/container still running?
```

If it is no longer running before it has submitted an accepted completion, the worker is faulty and Tulid must execute the normal failed-worker flow.

## Required architecture

Create or consolidate a distinct worker-observability component under the executor/runtime layer. It must:

- be owned by the executor, not the scheduler;
- monitor each active worker/container at a bounded interval (about once per minute, configurable for tests);
- check actual process/container liveness, not GPU usage and not stale job status;
- distinguish a normal completed worker from an unexpected exit:
  - accepted completion / terminal executor result: normal;
  - worker exits with no accepted completion: faulty/failed;
  - completion currently being validated: keep the worker/job alive until validation finishes, unless the process is actually gone;
- notify the executor through an internal callback/event when liveness fails;
- never parse or classify OpenCode text errors;
- never use `doom_loop`, `Unauthorized`, or log-text matching as a condition.

## Failure flow

```text
worker/container starts
→ executor registers worker with observability
→ observability checks liveness periodically
→ worker unexpectedly disappears
→ observability emits WorkerExited(job_id, attempt_id, returncode if known)
→ executor atomically marks job failed/orphaned
→ executor stops/cleans any remaining process/container
→ executor scrubs that worker workspace
→ executor releases the worker/job lease
→ task remains in its existing Todo state
→ scheduler sees no active job and schedules a fresh worker attempt
```

Do not move the Kanban task merely because a worker died. Do not add a cooldown. Do not require contract regeneration. The next attempt uses the same task and global command-only contract.

## Race and identity requirements

- Key supervision by job_id plus attempt identity, never task ID alone.
- Register liveness before/around process start so immediate exits are caught.
- Make failure handling idempotent; duplicate health notifications must not create duplicate retries or cleanup races.
- Do not mark a job failed if an accepted completion has already finalized it.
- Do not treat a normal process exit after successful completion as a fault.
- Do not mistake an old process, old workspace, or old job event for the current attempt.
- Ensure the scheduler cannot leave a task marked active merely because an executor callback was missed.

## Workspace cleanup ownership

The executor owns workspace lifecycle. After an unexpected worker exit it must clean the current job workspace automatically, including generated files, while preserving durable task history/events. Cleanup must be safe and idempotent.
